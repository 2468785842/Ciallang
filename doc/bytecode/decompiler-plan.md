# 可组合字节码反编译器方案

状态：设计提案，尚未实现。目标是从自产编译产物和 TJSCompile/TJSCompiler 产物恢复可读、可重新编译的 TJS2 源码，不要求字符级还原。行为保真优先于接近原始写法。

## 1. 决策与交付边界

采用统一内部层路线：输入适配器提供程序结构和函数体，反编译核心统一分析，再由 TJS2 后端输出。**一个内部反编译核心可以服务两类入口，但裸 Ciallang 指令流不足以覆盖任意 TJS2 字节码。** 必须补齐加载适配器、程序元数据、源操作语义及位置映射。

```text
TJSCompile 文件 → Reader → TJS2 适配/转译 ─┐
                                        ├→ ProgramIR → 分析/结构化 → TJS AST → Printer
自产源码 → Parser → IRGenerator → Chunk ─┤                                ↓
内部编码包 → Decoder + 常量/元数据 ──────┘                      文本 + 映射 + 诊断
```

ProgramIR 的函数体以现有 TAC 为基础；丢失语义的操作须在转译前保留高层节点或在 TAC 中增加精确操作。不能先丢失信息，再让反编译器猜回来。未来其他输入格式实现适配器即可复用分析和输出。

第一版采用 C++ 接口注册实现可插拔和显式组装，不先设计 DLL ABI、动态插件发现或通用格式转换寻路。运行时后端可以继续使用当前 Chunk；反编译适配器必须声明语义损失，严格输出不可接受有损路径。

“必须支持 tjscompile”作为正式验收入口。当前仓库验证的是 `TJS2 100\0` 文件格式，不凭工具名称或扩展名承诺其他版本：M0 固定实际 TJSCompile 二进制、版本/哈希、导出选项及样本；先识别文件头，再选择适配器。现有 `../TJSCompiler` 可作为一个参考实现，不能自动代表用户使用的所有 tjscompile 版本。

## 2. 当前实现核对及讨论修正

| 讨论假设 | 仓库实际情况及设计影响 |
|---|---|
| flag 全部变为普通寄存器 | `mapping.md` §3 和 `TjsTranslator.cpp` 有比较/测试与跳转融合，仍使用 `_zf`。分析必须把 flag 作为显式定义/使用，或先规范化为虚拟布尔值。 |
| 75 条统一三操作数指令 | 当前内部指令文档列 95 条；`CallV` 等有变长实参，不应依赖旧数量或固定三操作数。以 `Instruction.hpp`/`Bytecode.hpp` 枚举与操作数描述为准。 |
| Optimizer 未接线 | `IRGenerator.hpp` 默认传入 `optimizeDefaultChunk`；`Optimizer.cpp` 已有拷贝传播、整数传播、死加载清除及比较融合。自产入口要同时支持优化前后，早期可通过已有策略参数关闭优化辅助调试。 |
| 转译器仍待 M1 开始 | `TjsTranslator.cpp` 已实现扫描发射、跳转回填和类装配。新增来源记录应接入现有扫描，不重新设计一遍加载流程。 |
| 每个 Chunk 补 Rlc 就够了 | `Chunk::toBytecode()` 原地把 Rlc 的 TAC 下标换成字节码偏移。稳定来源表必须独立保存坐标空间，不能复用会变义的数字。 |
| Reader 的 sourcePos 可以直接当行号 | `TjsContext` 保存 codePos/sourcePos，不能在缺失源码文本时假定能恢复真实行列。无调试信息也必须可反编译。 |
| 现有 SSA 可直接全量复用 | `SSA.hpp` 明确拒绝 `CallOmit/CallExpand/CollapseArgs`，也未建模 `_zf` 和属性内存。先补访问描述，或对这些函数采用保守数据流分析。 |
| `+=` 逆融合即可修好属性行为 | `mapping.md` §6/§8 明确多条读改写不能完整替代一次 `Operation()`。逆融合可以恢复原始 TJS 操作，但不能同时证明现有转译执行也等价。 |

程序结构来源见 `TjsBytecodeReader.hpp`、`TjsTranslator.hpp`、`vm/Constant.hpp`。类体在加载期解释，部分原始结构不在 Chunk 中；需要保留 context 图、成员关联及初始化顺序。现有 FuncMeta/ClassMeta/PropMeta 是运行时表示，不能当作完整的反编译归档。

## 3. 行为一致的契约

分别验收两件事：

1. 输入字节码与生成源码在同一参考语义、同一宿主环境中的可观察行为一致。
2. TJS2 输入经转译在 Ciallang 中执行，与参考引擎执行一致。

两者必须分别报告；第一项通过不能掩盖第二项的转译近似。源码重编译后的 opcode、寄存器分配与文件字节允许不同。

可观察项包含返回值及类型、输出、全局/对象状态、成员访问与调用的次数和顺序、this 绑定、异常值和捕获范围、实参省略/展开、对象身份与共享关系，以及有脚本可见终结行为的生命周期。GC 的内部收集时刻不要求相同，但新增临时值导致可见 finalize 行为变化时不得忽略。

严格模式的结果状态为 `Success` / `Unsupported` / `InvalidInput` / `InternalError`，另记录逐样本验证结果。成功表示所有经过的转换满足已支持语义规则；测试覆盖不等于任意程序等价的形式证明。`Unsupported` 给出 context、来源位置和原因，不生成可误当成完整程序的成功文件。

反汇编或带缺口的阅读稿另设显式诊断模式；不能把 TODO 注释、空函数或运行期报错占位符当作完成的反编译。

需提前识别的不可恢复边界：

- 局部名通常可重新命名，但 eval/动态源码可能按名字访问局部；名字缺失时不能无条件改名并声称等价。严格模式对无法证明安全的动态求值拒绝输出。
- 异常堆栈、脚本文件名及行号可能被脚本观察。源码重排天然改变这些值；要求它们也一致时须有宿主位置映射支持，否则报告该限制。
- 任意宿主对象、动态类注册、调度标志若没有 TJS 语法等价表达，不能用普通属性读写近似。
- 插入状态变量/临时变量会影响动态名字查找、with、eval 和局部值保活。仅“生成名字不冲突”不足以保证安全。

## 4. 数据模型与接口

建议放置 `src/decompile/`，先保持独立库模块，避免依赖 CLI 和执行入口。

| 组件 | 契约 |
|---|---|
| `IInputAdapter` | 探测格式/版本，读取并验证输入，生成 ProgramIR 与能力/损失记录；不执行输入脚本。 |
| `ProgramIR` | 稳定 context/function ID、入口、父子/引用图、常量图、函数体、异常区域、名字与签名、类/属性结构、初始化动作的有序序列。 |
| `BodyIR` | TAC 操作及必要的精确语义节点；显式寄存器、flag、调用参数、正常/异常边；各节点关联稳定来源 ID。 |
| `IPass` | 声明前置条件和生成能力，返回修改结果及来源关系；不知道的操作保留或拒绝，不自行猜测。 |
| `ITargetBackend` | 检查目标方言能力，将结构化 IR 降为 TJS AST，生成文本和映射。 |
| `DecompilerPipeline` | 显式组装 adapter、分析 pass、结构化 pass、backend；提前校验能力组合。 |
| `DecompileResult` | 状态、文本、源映射、结构化诊断、输入/工具版本及采用的转换路径。 |

能力应包括精确属性操作、null 区分、proxy、异常、动态类、调用省略/展开、来源信息等。规则匹配依赖操作语义和数据流，不依赖输入文件名。来源模板信息只作有验证的加速路径，通用 TAC 分析仍需支持无模板来源的自产产物。

ProgramIR 优先使用拥有的字符串、常量描述与稳定索引，不长期借用 Atom 编号或裸 GC 指针。若适配期间必须持有 Chunk/元数据，使用符合 `Runtime.hpp` 的根保护，覆盖整个适配/分析期；Translator 析构后其原有根保护已结束，不能直接保存返回结构中的裸指针继续工作。输入引用图允许共享和环，须验证并显式表示，不能递归复制成树。

### 来源表从第一批开始实现

输出至少是 `{text, sourceMap, diagnostics}`，来源表独立于运行时 Rlc：

```text
输出文本范围（行/列或 UTF-8 字节范围）
  ↔ Program/Context ID + 稳定指令 ID 集合或多个 TAC 半开区间
  ↔ 原 TJS2 context + 码字半开区间
  ↔ 可选原源码偏移/行列
```

同时保存 `TAC index ↔ Cial bytecode byte offset`，标注空间和版本。转换可多对多，不能只取 min/max 混入无关指令；缩进、括号及生成声明可标为 synthetic。按行视图由范围表派生，空行可无来源。

TJS2 扫描对每条原始指令记录展开区间；融合的比较/跳转合并其来源，NOP/DEBUGGER 等零发射指令保留空区间/锚点，prologue 标为 synthetic。原源码位置确实可解析时再填 Rlc；无源码时保留码字来源，不伪造原行号。优化、压缩、结构化及打印均需传播来源关系。

## 5. 分析与恢复流程

1. **校验与归一化**：验证常量/context 引用、跳转边界、寄存器范围、调用参数布局和异常区域；将 Push/Call 与 CallV 统一为有序调用节点，保留省略/展开种类、接收者、丢弃结果及实际参数窗口。
2. **语义补全**：显式化 flag 数据流、proxy 查找、原始/普通属性访问、构造调用与普通调用。来源中 `NEW` 的含义不能在变成普通 Call 后丢弃。
3. **CFG 与数据流**：复用并核对 `ControlFlowGraph.*` 的正常/异常边；构造支配、后支配、循环、到达定义、活跃性及 def-use。异常发生时寄存器可能处于指令执行的中间状态，不能仅把块末值送进 catch。
4. **表达式恢复**：起步保留显式临时值和原执行顺序；只有证明单次求值、无额外异常/别名影响时才内联。getter、动态转换、调用、分配及 `Load` 实例化均不可按普通纯表达式处理。
5. **结构化**：恢复 if/else、循环、break/continue、短路/三元、switch 与 try/catch。跨块折叠需要支配/后支配和副作用条件；比较链只有证明比较顺序及贯穿语义等价才输出 switch。
6. **程序组装**：由结构元数据重建函数、property、类、extends、构造与字段初始化。保留声明安装顺序、共享函数身份与求值时机；不能把每次 Load 创建闭包都提升成一个共享函数。
7. **TJS AST 与打印**：建立适合输出的 AST，独立处理优先级、括号、转义及保留字。整数边界、负零、NaN/Infinity、Octet、共享/常量容器需逐类验证表达方式；不可用数值转字符串的默认格式猜测保真性。

### 属性读改写必须先解决语义

对 TJS2 的成员 Operation 保留原操作、对象、成员、RHS、结果需求及 flags，形成明确的 `PropertyUpdate` 语义节点。可选择在转译时新增精确 TAC 指令供 VM 实现，或先让无损反编译适配路径保留高层节点；后者仍不能满足“转译执行也一致”的最终验收。

`GProp + Add + DProp` 不能无条件改写为 `+=`。只有来源确认它就是一次原始 Operation，或已证明当前对象协议下完全等价，才可合并。自产源码本来就是显式读写时也不能强制合并。对 `obj()[key()] += rhs()`、前/后置自增、getter/setter 修改对象、异常中断及自定义宿主 Operation 分别验收。

### 无法直接结构化的控制流

优先保留常规 TJS 结构；允许对已证明安全的区域输出 `while + switch(state)`，但状态机不是任意程序的通用保真兜底。额外变量、try 区域和 with 栈可能改变行为；禁止跨异常区域随意搬运指令，禁止用一个外围 catch 替代嵌套 handler。

第一版对不可约 CFG、无法表示的 handler/动态作用域组合返回 Unsupported。后续单独实现并验证区域级状态机，验证不通过的输入仍拒绝；不输出 TJS 不支持的 goto，也不嵌入原始字节码解释器冒充可读源码。

## 6. 实施批次和完成条件

| 批次 | 内容 | 可检查的完成条件 |
|---|---|---|
| M0：兼容契约 | 固定目标 tjscompile/参考二进制、探测导出和运行能力，收集有/无 debug 样本，列输入版本及差异清单 | 参考脚本确实按输入路径执行；导出头/版本可识别；报告哈希和配置；未知版本被拒绝。 |
| M1：接口与来源 | ProgramIR、两个 adapter、结构元数据和常量图、来源表、严格诊断、输入校验 | 无执行地导入自产与 TJS2 样本；类/属性/签名及来源不丢；Translator 销毁和主动 GC 后仍安全。 |
| M2：语义闭环 | PropertyUpdate、null、proxy、typeof 缺失成员、构造/调用等差异；完成 flag/调用访问描述 | 对每个差异有参考最小用例；无损路径通过；未完成能力明确拒绝。扩充 TAC 时同步编码、dump、VM 派发与文档。 |
| M3：最小反编译 | 顺序体、字面量、局部/全局、普通调用和 return，AST/Printer，CLI 与 round-trip runner | 第一条两入口端到端；优化前/后样本均测试；输出范围可追溯；错误不会留下成功文件。 |
| M4：常规控制流 | if、循环、短路、三元、switch、临时值清理和命名 | 路径副作用、贯穿、break/continue、条件求值次数均对拍。 |
| M5：完整程序 | 类、继承、property、初始化顺序、闭包/绑定、with、异常、可变参数 | 支持范围内完整程序可重新编译；异常恢复、重抛和 GC 生命周期用例通过。 |
| M6：覆盖扩展 | 安全状态机、更多编译器产物/选项、模糊与变异测试 | 能力矩阵逐项验收；未支持集合可量化；独立二进制语料回归稳定。 |

M1 同时保存全部结构信息，M5 才实现相应的完整源码组装。M2 和 M3 按已无损的子集增量交付，不等待所有差异修完才开始端到端测试。M3 只代表可用的最小闭环，不代表“任意 TJS2 字节码反编译器完成”。

暂不依据“每块一两周”承诺工期。M0/M1 后以真实产物的语义缺口和 CFG 形态重新估算；属性协议、异常及动态作用域是主要不确定项。

## 7. 验证闭环

沿用 `tests/tjs/` 的脚本断言与 CTest；内部图、来源和 GC 所有权用 Catch2，并在 `tests/CMakeLists.txt` 显式登记。新增 runner 参考 `bench/bytecode_conformance.py` 的路径探测、哈希、超时及无损输出记录。

| 环 | 比较对象 | 发现的问题 |
|---|---|---|
| 自产 round-trip | 源码在 Ciallang 执行 vs 内部产物反编译再编译执行 | 内部分析、打印和自产优化后的恢复错误。 |
| TJS2 源码对拍 | 同一个 TJSCompiler 中原源码 vs 其字节码的反编译源码 | 原操作恢复及目标 TJS2 语法问题。 |
| 字节码真实性 | 参考引擎加载原字节码 vs 参考引擎运行反编译源码 | 无源码产物及参考源码/字节码路径差异。当前参考 main 的 `--dump` 不等于已有加载运行 CLI；需验证或补测试适配入口。 |
| 跨引擎执行 | 参考执行 vs Ciallang 源码执行、TJS2 转译执行及反编译源码执行 | 转译语义损失及两引擎共用错误。 |

除 stdout 逐字节外，测试脚本应主动记录类型、结果、状态和副作用序列；宿主协议用受控绑定记录派发。stderr 的脚本输出与工具计时/诊断分通道处理，不能靠剥离业务文本消除差异。返回码、异常、崩溃、超时分别报告；随机/时间类输入固定环境。参考侧不稳定用例独立记录，不能计为通过。

重点语料覆盖：无 debug、优化前后、flag 跨块、对象/键/RHS 单次求值、raw property、setter 抛错、this/global proxy、null/void、NEW 与 CALL、缺省/省略/展开实参、动态父类、字段顺序、短路返回值、switch 贯穿、嵌套 try/catch/重抛、with、eval 名字依赖、共享容器及闭包身份、临时值导致的 GC 保活变化。按 `doc/grammar/tjs.y` 建形态清单，同时加入不受编译器常规模板限制的合法字节码变异。

验收报告保留每个输入哈希、工具版本、转换能力、输出文件、状态和首个差异。公开“成功/不支持/无效输入/参考故障”的数量，不将跳过项计入成功。

## 8. 预期使用方式（提案）

```text
cial decompile input.tjsbc --from tjs2 --target tjs2 -o restored.tjs --map restored.map.json
```

默认严格输出，无损支持的程序才成功退出并生成结果；支持按文件头探测，显式 `--from` 用于覆盖有歧义的探测。具体参数在 CLI 接入批次确定，不表示现在已可使用。

宿主通过注册 adapter/pass/backend 组装同一管线。首批注册 `Tjs2InputAdapter`、`ChunkInputAdapter` 和 `Tjs2SourceBackend`；独立内部字节码文件输入在明确常量、Atom、元数据及版本封装后增加，不能把 `Chunk::code()` 的裸字节数组当成完整持久化文件。

本方案的实施起点是 M0/M1：先建立无损程序表示和可追溯来源，再从最小闭环扩展恢复能力。现有 TAC、CFG、SSA 和 Printer 基础可复用，但“逻辑不能错”最终取决于语义信息是否保留及逐阶段验证，不能仅靠模板查表保证。
