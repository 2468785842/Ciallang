# SDK、开发工具与模块化路线图

状态：规划；2026-10-31 记录。本文件定义后续方向和验收条件，不代表能力已经实现。
已确定脚本接口声明文件扩展名为 **`.d.tjs`**。具体声明语法、协议字段和模块加载入口
仍需专题设计；本文中的目录布局是目标布局。

项目定位为可嵌入的 TJS2 兼容运行时，开发工具独立发布；现代模块能力作为扩展逐步加入。
优先稳定核心与工具的接口，再拆分仓库，避免各端重复实现语言规则。
实际支持范围仍以[语法说明](syntax.md)、[兼容性说明](compatibility.md)和
[宿主集成](embedding.md)为准；可执行任务索引见[待办](../TODO.md)。

## 1. 当前基础与缺口

| 领域 | 当前实现 | 尚缺能力 |
|---|---|---|
| 宿主集成 | CMake 子目录库目标、Runtime/Context/VM、声明式绑定 | 完整安装包、明确公共头边界、版本化 SDK 和独立安装验收 |
| 代码分析 | Python stdio LSP，调用 CLI 取得编译诊断，另行维护符号分析与内置成员表 | 核心前端统一分析、接口元数据、声明文件和不完整源码分析 |
| 脚本加载 | `Scripts.execStorage()` / `evalStorage()`，文件读取和嵌套执行 | 独立模块环境、显式导出、模块缓存及统一解析接口 |
| 调试 | 字节码行号、调用帧、局部变量信息、执行路径导出；`debugger;` 打印状态并触发原生调试中断 | 脚本暂停/恢复、源码断点、单步、可供编辑器调用的调试接口 |
| 编辑器 | VSCode 客户端、高亮与语言配置，仍与核心同仓库 | 独立工具仓库、发行与兼容性检查 |

实现依据：`CMakeLists.txt`、`src/Binding.hpp`、`src/runtime/Runtime.hpp`、`src/vm/VM.hpp`、
`tools/lsp/cial_lsp.py` 的 `DefinitionIndex` / `BUILTIN_MEMBERS` / `check`、
`src/stdlib/ScriptsLib.*`、`src/vm/VMState.cpp` 的 Debugger 派发、`Rlc.hpp`、`CallFrame.hpp`、
`Constant.hpp` 的 `FuncMeta::localVars` 及 `editors/vscode/`。
目前的 `import` / `export` 保留字也不代表已具备模块语义（`src/parser/Token.hpp`、`Parser.*`）。

## 2. 两仓库边界

| 目标仓库 | 职责 | 主要交付物 |
|---|---|---|
| `Ciallang` | 编译器、VM、标准库、模块加载、权威代码分析、核心调试接口 | CLI、C++ SDK、接口声明与元数据、版本/能力描述 |
| `ciallang-tools` | LSP 服务、DAP 调试适配器、VSCode 客户端、高亮和编辑器集成 | 语言服务、调试适配器、VSIX、编辑器验收测试 |

`ciallang-tools` 为计划名称，尚未创建或迁移仓库。LSP 与 DAP 是不同职责，放在同一工具仓库
并不意味着合并协议。核心提供分析和调试能力，工具负责协议适配及编辑器生命周期管理。

语言规则、作用域与类型分析以核心前端为权威。当前 Python LSP 可保留作为过渡，逐步消费
核心的结构化分析结果，不再长期扩展另一套独立解析器。后续分析接口应能处理未完成输入，
明确区分语法恢复、部分符号结果和完整编译成功；不能简单把失败编译视为没有符号。

迁移前先建立版本、协议/元数据 schema 版本和能力查询约定。工具依据实际能力启用功能，
对版本不兼容给出明确诊断。分析请求不执行被分析的用户脚本。具体使用 CLI 进程还是
常驻分析会话、如何增量更新，在接口专题中确定，不提前绑定 Python 或 C++ 实现语言。

工具仓库应自行维护服务端源码，不再在打包时从核心仓库的相对路径复制；核心也不包含编辑器
专用实现。两端独立发布，并用支持的版本组合做集成验收，包括未安装 Python/解释器、
路径含空格与中文、打开工程子目录等情况。迁移不得丢失已有协议和宿主测试。

## 3. SDK 与 `.d.tjs` 声明文件

### 3.1 给 C++ 宿主的 SDK

目标发布布局为公共头目录、库、CMake package 配置及独立嵌入示例。公共接口应覆盖
运行时创建、脚本编译/执行、宿主注册、结构化诊断、资源解析，并明确 Value/Handle/RootGuard
持有关系、GC 与异常传播约定。内部 VM/IR 结构不因当前头文件可被包含就自动成为稳定接口。

第一版应实现 install/export、依赖传递、版本信息与 `find_package(Ciallang CONFIG REQUIRED)`，
继续提供 `Ciallang::Ciallang` 目标。验收程序在安装目录之外构建，不能依赖源码树或构建树头文件；
Windows、Linux、macOS 均验证基础嵌入和原生绑定。具体头文件布局在 SDK 设计中收敛。

初期承诺明确范围内的 C++ 源码兼容及工具链要求，不承诺跨编译器、运行库和动态库的稳定 ABI。
若后续确需动态插件或跨语言嵌入，再设计较窄的 C ABI；不顺带承诺活跃模块卸载。

### 3.2 给脚本工具的声明文件

**扩展名固定为 `.d.tjs`**，例如 `stdlib.d.tjs`、`host.d.tjs` 和 `foo.d.tjs`。
它描述可用接口，不执行实现，也不等同于 C++ 头文件。

声明模型需要表达函数、参数、返回值、类、属性、继承、文档及必要的可选/变长参数信息。
声明语法尚待设计，不直接照搬 TypeScript 语法。现有 `.tjs` 类型注解会被解析并忽略，
不能据此宣称已实现静态类型检查或声明模式。

先建立版本化 API 元数据模型，再让导出器、`.d.tjs` 解析器、LSP 和文档生成共享该模型。
从 C++ 绑定中导出可确定的签名，动态回调、默认值或无法自动推导的返回类型需补充元数据；
不制造虚假的确定类型。标准库补全逐步由该模型提供，替代手写的内置成员表。
宿主可随 SDK/应用发布声明及导出元数据；LSP 读取产物，不为取得补全而自动运行宿主程序。

声明文件需要专用读取/分析模式。实现时必须同步处理以下边界：

- CLI、`Scripts` 和模块加载器不得将 `.d.tjs` 当普通脚本执行，应给出明确的声明文件诊断。
- CTest 登记、脚本 runner、基准与相关 `*.tjs` 扫描应排除声明文件，声明解析另设测试。
  当前 `tests/CMakeLists.txt` 和 `tests/run_tjs_tests.py` 尚未提供这项排除。
- 编辑器识别 `.d.tjs`，允许导航和补全，同时区分声明诊断与普通脚本编译诊断。
- 为同名实现、宿主全局声明、标准库声明制定查找优先级和冲突诊断；这些规则与项目配置
  一同设计，不能仅靠扩展名猜测运行时加载行为。
- 声明不增加运行时导出，不改变模块初始化顺序；实现与声明的一致性检查单独定义。

本路线图阶段不新增可执行声明样本，避免现有脚本扫描器误收集。
声明/实现分离的设计参考：[TypeScript 声明文件](https://www.typescriptlang.org/docs/handbook/declaration-files/introduction.html)、
[Python stub 分发规范](https://typing.python.org/en/latest/spec/distributing.html)。

## 4. `Scripts` 兼容层与新模块系统

继续保留现有 **`Scripts`** 命名空间的 `execStorage()` / `evalStorage()` 作为 TJS2/Kirikiri
兼容入口，保持既有脚本执行、全局可见性、返回值和异常行为；不把缓存模块加载语义塞入它们。
兼容入口的现有边界见 `src/stdlib/ScriptsLib.*` 及[兼容性说明](compatibility.md)。

新模块系统单独设计模块环境与加载器，再决定对外函数名。第一阶段不增加 `import/export`
语法，也不把普通脚本通过字符串拼接包装为函数来模拟模块作用域。

| 规则 | 目标语义 |
|---|---|
| 作用域 | 模块拥有自己的顶层绑定；标准库/宿主环境按明确规则可见，模块变量不泄漏到全局 |
| 导出 | 显式导出；导出容器、可变绑定与只读性另行定义 |
| 解析 | 相对路径相对导入模块，由宿主解析接口确定；规范模块身份供运行时、LSP、调试器共用 |
| 缓存 | 每个 Context 内按规范模块身份缓存成功加载的模块；缓存持有关系纳入 GC |
| 循环依赖 | 第一版明确拒绝并报告完整依赖链，不返回半初始化模块 |
| 加载失败 | 清理加载中状态及临时根，异常按既有脚本协议传播，后续允许重试 |
| 存储 | 支持宿主文件、归档或虚拟资源解析；运行时与编辑器使用一致的解析规则 |

验收包括重复加载、相对路径别名、宿主虚拟资源、模块间隔离、导出可见性、循环依赖、
失败后重试，以及加载/异常过程中的强制 GC；原有 `Scripts` 测试保持通过。
动态拼接路径无法静态解析时，工具明确回落，不伪造确定的导入目标。

模块语义稳定后，再讨论 `import/export` 语法、TJS2 兼容模式边界和后续包管理需求。
模块加载能力、声明文件查找和包管理是相关但不同的设计，不在第一版同时扩展。

## 5. 脚本调试器与 DAP

核心提供调试控制与状态检查接口，工具仓库通过
[DAP](https://microsoft.github.io/debug-adapter-protocol/overview) 对接编辑器。
LSP 继续负责代码分析；调试协议和脚本 stdout/stderr 使用清晰隔离的通道。
现有原生中断与状态 dump 不作为脚本调试协议。

先补齐调试基础：持久的源码身份及完整来源、源码/字节码位置映射、局部变量的有效范围与
存储位置、调用帧的可检查状态。动态执行、`Scripts` 嵌套执行和模块加载的源码均需可追踪。
暂停期间保活被查看的对象，恢复执行后使本次暂停的对象引用失效，避免过期引用或 GC 悬空。

第一版支持启动脚本、源码行断点、`debugger;` 暂停、继续、单步进入/跨过/跳出、调用栈、
参数与局部变量、`this`、异常暂停及输出转发。不可执行位置的断点应明确反馈是否绑定、
实际绑定位置，不能在编辑器中伪装成已生效。

第一版使用关闭优化和 JIT 的显式调试模式，以源码位置和变量准确性为验收前提。
对象查看默认读取原始值，不调用 getter；暂不提供任意脚本表达式求值、条件断点、
修改变量、远程 attach 和优化执行调试。后续能力逐项声明，未实现的不报告为支持。
调试检查只在启用调试的执行路径生效，默认执行路径须通过同机 Release 对照验证。

验收使用真实 DAP 会话覆盖断点命中、单步、递归、异常及嵌套脚本、源码定位和暂停期间 GC，
再由 VSCode 宿主验证界面接入；协议通过与界面验收分别记录。

## 6. 实施顺序与交付条件

在完整 SDK 和仓库拆分前，先完成 CLI 发布基础：统一版本、安装/CPack 规则、独立解压验收和
Release CI。该基础已实现并通过本机 Windows 验收，跨平台远端发布验收仍待运行，
详见[发布指南](releasing.md)。首次 CLI 预览版不代表 SDK 已完成。

| 批次 | 主要交付 | 完成标准 |
|---|---|---|
| 1：SDK 与工具边界 | 公共 SDK 边界、安装导出、版本/能力约定、源码身份基础；随后拆分仓库和发行 | 三平台安装后独立工程可编译运行；工具不依赖核心源码树，版本不兼容明确报错 |
| 2：接口声明与分析统一 | API 元数据、`.d.tjs` 声明模式、标准库/宿主导出、核心分析接口 | 实际宿主接口可由声明提供补全与导航；声明不被执行/登记为脚本测试；不完整源码有可用分析结果 |
| 3：模块系统 | 模块环境、显式导出、统一解析、Context 缓存及失败恢复 | 隔离/缓存/循环/重试/GC 验收通过，且 `Scripts` 兼容行为保持 |
| 4：DAP 调试器 | 核心检查/控制接口、DAP 适配、VSCode 调试接入 | 断点、单步、调用栈、变量及异常暂停形成端到端闭环，默认执行性能经过复核 |

各批次先形成接口说明和最小可用实现，再扩展能力。源码身份和运行时持有关系在第一批就明确，
避免模块和调试器后续重复重构；SDK 不必等待全部语言工具能力才能首次发布。

暂未定案：公共头文件具体布局、分析/调试接口的传输形式及字段、`.d.tjs` 具体语法与查找
优先级、模块加载函数名与导出绑定规则，以及未来 `import/export` 语法。仓库迁移和 SDK 发布
在各自实现批次执行，CLI 发布基础的实际状态以发布指南为准。
