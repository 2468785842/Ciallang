# 诊断与源码位置重构计划

状态：实施中，2026-10-31 首批落地（批次 0–4 完成，批次 5 完成故障指令定位，其余见文末"实施状态"）。目标是让 Lexer、Parser、代码生成和 VM 的错误具有可靠的源码身份、范围和上下文，并让 CLI、宿主与 LSP 消费同一份结构化诊断。

## 1. 当前实现与问题

| 环节 | 已有基础 | 需要处理的问题 |
|---|---|---|
| 源码 | `src/common/SourceFile.*` 提供字节缓冲、行索引、列换算和源码摘录 | `SourceLocation` 只有行列，没有源码身份，也不能区分未知位置与文件开头；NUL、非法编码等读取错误缺少位置；行表尚未建完时的错误也要可定位 |
| Lexer | `src/parser/Lexer.*` 为 Token 填充范围，错误可通过 Token 传递 | 多处分支使用 `pos() - 1` 作为包含式结束位置，可能落在 UTF-8 字符内部；Invalid 分支按读取后的游标定位；`getRowCol()` 直接解引用行查询结果，需要验证 EOF、空文件和非法输入边界 |
| Parser / IR | `Parser.hpp`、`IRGenerator.hpp` 已通过 `SourceFile::error()` 产生上下文 | 错误数据与已格式化的文件名、行列和彩色摘录混合；需要核查所有失败路径、Token/AST 范围以及重复或丢失词法错误的问题 |
| CLI / 宿主 | `SourceFile::error()` 已生成 `ResultMessage::details()` | `src/cli/Diagnostics.cpp` 只打印 message；`VM.hpp` 另有 eval 错误输出，展示入口分散 |
| VM | `Chunk::addLine()`、`lineAtBc()`、`Rlc` 已提供语句级映射 | `VMState.cpp` 原生异常分支把行号拼进异常 message，没有统一的源码身份和栈；`VMState.hpp` 明确 PC 为下一条指令，需要验证错误路径使用 `pc` 是否错位，优先使用实际故障指令起始位置 |
| LSP | `tools/lsp/cial_lsp.py` 调用 `--check-json`，转换 UTF-8 字节列到 UTF-16 | 当前对 endColumn 加 1，并用正则剥离 message 中的位置前缀；检查器使用临时 `document.tjs`，没有保留原文档身份；检查同步执行，快速输入时可能阻塞后续请求 |

以上为代码阅读结论和待验证风险；首批通过最小复现明确具体错误，不把每个风险直接当作已证实缺陷。

## 2. 统一约定

### 源码与范围

- 内部以 UTF-8 **字节偏移的半开区间 `[begin, end)`** 为权威，行列均从 0 开始；CLI 展示时转为从 1 开始。
- Token 范围覆盖原始词素，不能用解码后的字符串长度推算；EOF 为 `[size, size)`，缺失 Token 可用插入点零宽范围。
- 未知位置显式为空，不使用 `(0, 0)` 充当未知值。所有范围满足 `0 <= begin <= end <= size`。
- 建议引入 `SourceId`、`SourceSpan` 和不可变源码快照。身份与内容版本分离；路径、URI、REPL/eval 虚拟名称都可以表示，具体命名在接口补丁中确定。
- 行索引统一处理 LF、CRLF、空文件、末尾换行与 BOM；非法 UTF-8 仍能按原始字节给出有界范围。字节列、UTF-16 列、终端显示宽度分别转换，不混用。
- 已编译 Chunk 共享所需快照或受控调试资料，不能借用编译时局部 `SourceFile`；跨 eval、闭包、宿主执行和 REPL 历史输入仍能找到当时源码。允许关闭源码正文保留，但保留身份/位置并明确降级为只显示文件与行列。

### 诊断数据与展示

基于现有 `Result` / `ResultMessage` 渐进演进，避免同时替换错误传播协议。建议诊断字段为：

| 字段 | 用途 |
|---|---|
| code、stage、severity、message | 稳定错误码、产生阶段、级别和纯文本说明；工具不能解析说明文字判断错误类型 |
| 可选 primary span | 主要报错位置；无位置的文件读取/宿主错误保持无位置 |
| labels / related locations | 开括号、声明位置、调用点等补充位置及说明 |
| notes | 修正方向或上下文说明 |
| 可选 stack frames | 运行时函数、源码身份、故障/调用位置；与脚本异常值分开保存 |

核心产生数据；终端渲染器负责路径、源码摘录、下划线、颜色和显示宽度，JSON 序列化器负责协议字段，LSP 负责 URI 与 UTF-16 范围。机器输出不包含 ANSI 或预拼接位置前缀。复用已有摘录能力，逐步移出 `SourceFile::error()`，无需引入第二套格式化逻辑。

错误码按词法、语法、代码生成、运行时、工具故障划分；首批只覆盖已迁移诊断并建立表，避免为了编号一次性改动全部文案。

## 3. 实施批次与验收

### 批次 0：建立复现和协议基线

阅读对应接口注释，盘点 `Result::error()`、`SourceFile::error()`、Error/Invalid Token、原生异常转换、顶层异常输出及所有位置消费者。补充小型复现，记录当前 CLI 文本、JSON 和 LSP range。

验收：每个确认的问题都能定位到产生位置、传递或渲染中的具体环节；明确现有 JSON 包含式 end 的兼容边界。不先批量改提示文字。

### 批次 1：源码模型与位置基础

修改入口：`src/common/SourceFile.*`、`SourceLocation.*`、`Result*`，以及 Token/AST 的必要适配。

- 建立字节范围、源码身份和快照查询接口；旧行列 API 通过适配层过渡，不能同时维护两套可独立修改的权威位置。
- 行索引与错误安全构建，覆盖空缓冲、EOF、CRLF、无末尾换行、非法字节。
- 明确快照持有、释放和关闭正文保留的策略；源码资料优先使用独立 C++ 所有权，若引入 GC 对象则按 `Runtime.hpp` / `gc.hpp` 接入标记。

验收：字节范围与行列转换有边界测试；中文、emoji 的起止位置落在字符边界；未知位置与首字符可区分；原 SourceFile 析构后快照仍可查询。

### 批次 2：Lexer / PreProcessor 定位

修改入口：`Lexer.*`、`PreProcessor.*`、`Token.hpp`。

- 用扫描起点和消费后的字节游标统一记录范围，移除各分支的 `pos() - 1` 推算。
- 核查空白/注释跳过、预读回退、正则与除法、模板字符串与嵌入表达式、预处理分支的位置。
- 非法字符指向实际字节；未闭合字符串/注释给出起始处与 EOF 关系。错误 Token 与诊断明确单一上报责任，不能被 Parser 丢失或重复报告。
- 保持 REPL 的 incomplete 判定，区分可以继续输入与确定非法输入。

验收：每类 Token 和失败路径都断言原始字节范围，至少覆盖中文、四字节字符、CRLF、EOF、非法 UTF-8/NUL 和预处理错误；扫描失败不会空指针解引用或停在原位置无限重试。

### 批次 3：Parser / IR 诊断与有限恢复

修改入口：`Parser.*`、`parser/ast/`、`IRGenerator.*`；先阅读 `doc/syntax.md` 与 `doc/grammar/tjs.y`。

- `expect()` 统一给出期望项、实际 Token 和范围；EOF 报缺失项，成对分隔符增加起始位置说明。
- AST 区分完整表达式范围与关键 Token 范围；非法赋值目标、上下文不允许的语句等 IR 错误指向相关表达式。
- 先稳定首条诊断，再加入面向编辑中的有限恢复：语句/声明边界同步，考虑嵌套分隔符；限制错误数量并保证游标前进。
- 分析模式允许部分 AST；存在错误时不能进入正常代码生成或执行。批量编译与 REPL 保持各自的终止/incomplete 约定。

验收：缺失括号、缺失表达式、错误声明与两个独立语法错误给出可理解位置；不产生大量级联报错；恢复不改变有效程序语义，不妨碍后续符号分析迁移。

### 批次 4：CLI、JSON 和 LSP 一起迁移

本批依赖批次 1–3，在同一兼容窗口更新生产者和消费者。

- CLI、REPL、`VM.hpp` eval 输出接入共享渲染器；输出文件、行列、错误码、源码及指示范围，支持无颜色输出。多行范围、Tab、宽字符和零宽插入点单独处理。
- `--check-json` 增加 schema 版本、范围语义、源码身份、错误码及相关位置。通过显式能力/版本字段区分旧版；旧字段如需保留必须由转换器派生。未知 schema 给出清晰错误。
- 为未保存内容提供编译检查输入及逻辑源码名称，例如标准输入加 source-name；传输临时文件与诊断身份分离，禁止把临时路径暴露到编辑器。具体 CLI 选项在本批确定。
- LSP 按 schema 转换半开范围，删除新版路径上的 `endColumn + 1` 和位置前缀正则；保留明确的旧版适配。用完整 UTF-8 字符边界转换为 UTF-16；零宽范围保持零宽。
- 映射 code、severity、relatedInformation；文档级无位置错误由适配器选择文档级展示位置，不能伪造核心范围。编译器诊断与检查器不可用使用不同错误码。
- 保留客户端原始 URI、未保存文本与版本；增加短暂防抖、可取消后台检查及过期结果丢弃，保证 stdio 写入有序、关文档清空，并终止遗留检查子进程。先用当前进程式检查，不把常驻分析服务作为本次前提。
- LSP 分析始终不执行脚本；运行时错误交给执行入口/未来 DAP，不混入静态检查。

验收：同一错误的核心范围、JSON 与 LSP 指向同一词素；中文/emoji 前后的下划线、EOF 与跨行范围正确；编辑器 Problems 可导航且无临时路径/ANSI；快速输入、修复、关闭、超时与旧版本检查器均有协议测试。

### 批次 5：VM 源码诊断与异常栈

可在批次 1 后独立推进，依赖批次 4 的统一渲染完成交付。先阅读 `VMState.hpp` 的 DispatchRet/ScriptExceptionCarrier、`VM.hpp` 的 callValue 以及 Chunk 生命周期约束。

- Chunk 关联源码身份/快照；沿嵌套函数和延迟执行传播。先复用现有语句级 Rlc，之后为可能抛错的操作补充表达式/调用点映射，精度不足时明确保留语句级位置。
- 故障位置使用派发前的指令起始 PC；调用者保存调用点位置，不能简单用下一条 PC 或任意减 1。检查原生绑定、getter/setter、构造、eval、回调重入和帧切换路径。
- 异常展开前捕获必要的值快照；诊断元数据随异常传播，保持首次抛出与重抛的策略一致。避免每次经过原生边界都重新加位置。
- 保留任意脚本 throw 值、try/catch/finally、ScriptExceptionCarrier 与 GC 根协议。源码和栈不再依赖修改 message 传递；迁移前锁定脚本可见 message 的兼容策略，并同步兼容性文档。
- 捕获栈不得执行脚本 getter、toString 或 finalizer；不因渲染原始异常再触发用户代码。栈条数有上限，原生帧、无源码字节码和尾调用优化可明确降级。
- 优化器压缩、TAC 到字节码、异常表、行号重映射一并验证；JIT 路径提供等价位置或明确的映射回退。沿用惰性编码，不为展示提前编码全部 Chunk。

验收：跨函数、跨文件、脚本/原生互调、重抛及 eval 错误显示正确故障点与调用点；被 catch 的错误不额外打印；编译源码释放、GC 与异常恢复后仍可靠；无调试资料时保持清晰的错误文本。

## 4. 验证与合并顺序

建议按批次拆为独立可审阅提交，位置基础迁移期间以适配器保持可构建；不把所有子系统改动塞进一个补丁。

| 层级 | 验证方式 |
|---|---|
| 基础/前端 | Catch2 精确断言字节范围、错误码与相关位置；新增 C++ 测试登记在 `tests/CMakeLists.txt` |
| 语言/异常 | `tests/tjs/` 检查可观察语义；内部异常元数据、GC/快照持有关系用 Catch2 |
| CLI | 扩充 `tests/cli_test.py`，检查 stdout/stderr、无颜色摘录、JSON schema；文本快照只覆盖稳定格式 |
| LSP | 扩充 `tools/lsp/test_protocol.py`，通过真实子进程验证 Unicode、版本竞争、关闭清空、URI、相关位置及兼容回退 |
| 编辑器 | 扩充 VSCode smoke 验收 Problems 范围与修复清空；CLion/IDEA 用通用 LSP 客户端手工验证中文与跨行导航，记录未验收范围 |
| VM/优化 | Debug/Release 相关测试与全量 CTest；启用 JIT 的配置验证异常点、映射与恢复；性能涉及正常派发路径时做同机 Release 基线对照，记录时间和源码资料内存成本 |

每批修改 C++ 后执行仓库 clang-format，运行受影响检查；集成后运行完整平台预设检查。诊断格式变化更新 CLI/LSP/宿主指南，脚本可见行为变化更新语法与兼容性说明。本计划与 `doc/roadmap.md` 的源码身份、SDK 结构化诊断和核心前端分析方向保持一致，不以拆仓、模块或 DAP 完整实现作为完成条件。

最终完成标准：所有有源码上下文的错误均可追溯到对应源码版本；CLI 有可读摘录，LSP 有精确可导航范围，宿主可取得结构化数据；错误恢复、异常传播、GC 与正常执行性能通过对应验收。
