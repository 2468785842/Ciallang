# Windows Release 类压力回退归因

Status: implemented（2026-11-10 归因并接受）

## 问题

结构化异常栈/getter 隔离批次后，Windows Release 的类压力用例（2 万次实例化）
出现约 +8% 回退，同机两次测量方向一致，尚未归因。

## 已知事实与证据

- 测量见[性能记录](../../../../doc/performance.md#2026-11-01-结构化异常栈与-getter-异常隔离)；
  该批次涉及异常表与调用帧路径，类实例化压力路径可能受异常表布局或帧构建影响。

## 归因与结论（2026-11-10，Windows 10 x64，VS 2022 LLVM clang 19.1.5 Release）

- **方法**：三方对照 before（`build/cial-before-stack.exe`，源码快照批次终态）
  / stack（2fe2d59 worktree 重建）/ head（7ab81e3）；原 2 万次负载总耗时约
  41 ms（含约 30 ms 启动，噪声占主导），改用 20 万次迭代 x10 负载，交替
  11 轮取中位数，并按构造/方法/getter 分解。
- **数据（会话内配对）**：full（构造+方法+getter）stack +2.4% / head +4.0%
  （第二会话 head +1.0%）；nogetter −3.4% / −1.6%；ctoronly −3.6% / −4.3%。
  构造与方法调用路径批次后**更快**。
- **归因**：回退完全来自 getter 异常隔离——每次属性 getter 访问额外分配一个
  哨兵调用帧（`allocCallFrame(&boundary)` + DEFER 回卷，`Property.hpp`）。
  full−nogetter 差值 ≈ +19 ms / 20 万次 ≈ **95 ns/次**（head 91 ns）。
  属常量开销，不是路径退化；异常表与实例化路径未新增每对象工作。
- **接受理由**：隔离是正确性修复——循环内直接访问 getter 的负载在 before
  二进制上崩溃（rc=127），旧嵌套 `run()` 会重复执行父帧语句；不得为性能回退
  可观察的异常语义。常量开销已量化，getter 密集负载总影响约 +1~4%。
- **后续优化候选**（未立批次）：把哨兵并入 getter 自身帧（帧上标记
  exceptionBoundary，unwind 到带标记帧即截停），可省一次帧分配/释放；需改
  异常派发的截停语义，按需评估。原始样本见[测量报告](../../../reports/2026-11-10-perf-attribution.json)。

## 完成条件

归因并处理（消除退化或记录接受理由），结论同步性能记录与本 note 状态。——**已归因并记录接受理由**（见上节）。

## 风险或备选方案

异常栈隔离是行为正确性改动，回退处理不得回退可观察的异常语义；
测量需注明 MSVC 版本与机器环境。
